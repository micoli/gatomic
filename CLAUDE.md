# gatomic

TUI to build atomic `git commit --fixup` commits, with native hunk/line
selection (no shell-out to `git add -p`). See README.md for user-facing docs
and `/Users/omichaud/.claude/plans/creer-une-tui-en-squishy-spring.md` for
the original design plan/rationale.

## Architecture

- `src/git/` — shell-out wrapper around the `git` binary (`repo.rs`), file
  status parsing (`status.rs`), commit listing (`commit.rs`). No `git2`:
  everything goes through `Command::new("git")` on `PATH`, deliberately, for
  cross-platform consistency (Linux/brew/Git for Windows).
- `src/diff/` — the core, most delicate part:
  - `model.rs`: `FileDiff`/`Hunk`/`DiffLine` data model.
  - `parser.rs`: parses one file's unified diff into `FileDiff`. Never
    touches multi-file diffs — always call `git diff` per file.
  - `patch.rs`: reconstructs a patch from a partial hunk/line selection and
    applies it via `git apply --cached`. Read the module doc comment before
    touching the offset math (`new_start` shifting, removed-line
    retrogression to context, the old_count==0 insertion-anchor special
    case) — it's easy to look right and be wrong. Any change here needs a
    real-repo integration test, not just a unit test on a string.
  - `load.rs`: picks `git diff` vs `git diff --no-index` depending on
    tracked/untracked status; untracked files deliberately reuse the exact
    same "new file" code path as tracked new files.
- `src/selection.rs` — per-file hunk/line selection state
  (`FileSelection`/`HunkSelection`). Toggling a hunk sets all its lines;
  toggling a line recomputes the hunk's own selected flag.
- `src/tui/` — one file per pane (`files_pane.rs`, `hunk_pane.rs`,
  `commits_pane.rs`) plus `layout.rs` (3-zone `ratatui::Layout`) and
  `mod.rs` (the `App` state machine + event loop). Each toggle in the hunk
  pane calls `diff::apply_selection` immediately (git add -p-style), which
  first resets the file's index entry to HEAD then reapplies the current
  selection from scratch — this makes every toggle idempotent regardless of
  toggle history, so don't try to make it incremental/diffed against the
  previous selection.

## Key invariants / gotchas

- `-n`/`--last-commits` is `Option<usize>`. `None` means "commits unique to
  the current branch" (`git::commit::commits_of_current_branch`), not "some
  default count". Don't give it a numeric default — that changes the
  documented CLI behavior (see AskUserQuestion history in the plan file).
- Fixup is committed with `git commit --fixup <sha>`. No squash, no
  autosquash in V1 (explicit user decision) — don't add those without
  checking with the user first.
- After a successful fixup commit, `App` clears all cached
  `FileDiff`/`FileSelection` state, because HEAD moved and any open diff
  snapshot is stale.

## Commands

```sh
cargo build
cargo test                              # unit + real-git-sandbox integration tests
cargo clippy --all-targets -- -D warnings
cargo fmt
bash tests/fixtures/init-test-repository.sh basic t   # demo repo in tmp/t, then:
cargo run -- -n 20                                     # from inside tmp/t
```

CI (`.github/workflows/ci.yml`) runs fmt/clippy/test plus a non-interactive
`gatomic --help` smoke check (the TUI itself needs a real terminal, so it's
not exercised end-to-end in CI — rely on `tests/diff_integration.rs`, which
drives the same `git`-backed functions the TUI calls, without crossterm).

## Testing conventions

- `tests/common/mod.rs`: shared `Sandbox` helper (throwaway repo + isolated
  git config), adapted from git-helper's `tests/cli.rs`. It changes the
  process's cwd and env vars, which are process-global — any test using it
  MUST hold `sandbox_lock()` for its whole body (see existing tests for the
  pattern). Don't remove that guard to "parallelize" tests.
- Prefer diffs generated by a real `git diff` inside a `Sandbox` over
  hand-written diff-text fixtures — hand-written ones drift from git's
  actual output format silently.
- Any change to `diff/parser.rs` or `diff/patch.rs` needs both: a unit test
  (fast, pins down parsing/reconstruction logic) and, if it changes staging
  behavior, an integration test in `tests/diff_integration.rs` that asserts
  on `git diff --cached`/`git diff` after a real `apply_selection` call.

## Style

Repo-specific reminders on top of the user's global conventions (English
code/comments, early returns, one component per file): keep one pane/one
git concern per file as the codebase grows — don't let `tui/mod.rs` grow
pane-rendering logic, and don't let `git/repo.rs` grow diff-parsing logic.
